# 9.1 实时处理解决什么问题

## 批处理与实时处理
| 比较项 | 批处理（第 4～8 章） | 实时处理（本章） |
|---|---|---|
| 数据 | 攒好的、有边界 | 源源不断、没有尽头 |
| 什么时候算 | 定时运行，如每天凌晨 | 一直运行，数据一到就算 |
| 结果多久出来 | 几分钟到几小时 | 几秒到几分钟 |
| 典型工具 | Hive、Spark | Kafka + Structured Streaming、Flink |
::: notes
实时处理不是要取代批处理。大多数报表“算昨天”就够了，批处理更简单、更省资源；只有“晚了就没用”的需求才值得用实时处理。
:::

## 三个典型场景
| 场景 | 要做什么 | 要多快 |
|---|---|---|
| 交易大屏 | 每分钟成交额、品类排行 | 几秒到一分钟 |
| 实时风控 | 异地多次下单、同卡多次付款，马上拦截 | 一两秒以内 |
| 实时推荐 | 刚看了什么，下一屏就推荐 | 一秒以内 |

# 9.2 Kafka：数据的快递中转站

## 为什么要放一个消息队列
- 直接推送：接收方重启，消息就丢了
- 大促流量十倍，接收方处理不过来拖慢下单
- 消息队列：发送方写完就走，接收方按自己的速度取
- Kafka 特别之处：读走后**不删除**，默认保留 7 天
::: notes
保留 7 天意味着同一份消息可以被多个系统各读一遍，某个系统出了问题还能回过头重读。Kafka 由 LinkedIn 开发，后来捐给 Apache。
:::

## 主题、分区和偏移量
- **Broker**：运行 Kafka 的服务器，随书环境 1 台
- **主题**：同一类消息放一起，如 `orders`
- **分区**：一个主题分成几份，读写可以并行
- **偏移量**：分区里每条消息的编号，从 0 开始
- 键相同的消息一定进同一个分区
::: notes
Kafka 对键做哈希再除以分区数取余数。用用户编号做键，同一个用户的订单就按先后顺序进同一个分区。
:::

## 生产者、消费者和消费者组
- 生产者写消息，消费者按偏移量**拉**消息
- 组内分摊：一个分区只给组里一个消费者
- 组间独立：各组记各自的偏移量
- 宕机或加入时“再均衡”，消息不丢
- **消费积压** = 最新偏移量 − 已读到的偏移量
::: notes
消费者个数超过分区数，多出来的会闲着。积压一直涨，说明消费者跟不上，要加消费者（不超过分区数）或优化处理逻辑。
:::

## 常用命令
| 要做什么 | 命令（都加 `--bootstrap-server localhost:9092`） |
|---|---|

## 用 Python 收发消息
```python
from kafka import KafkaProducer, KafkaConsumer
producer = KafkaProducer(bootstrap_servers="localhost:9094")
producer.send("orders", key=b"u001", value=json.dumps(order).encode())
producer.flush()                       # 确保缓冲区的消息都发出去
consumer = KafkaConsumer("orders", bootstrap_servers="localhost:9094",
                         group_id="screen", auto_offset_reset="earliest")
for msg in consumer:
    print(msg.partition, msg.offset, msg.value.decode())
```
::: notes
Kafka 只认字节，发之前编码，读出来解码。auto_offset_reset 只在这个组第一次读时起作用。实验 9-1 的生产者平均每秒发 20 笔，现实 1 秒相当于模拟 6 秒。
:::

# 9.4 Structured Streaming

## 把数据流看成无界表
!mermaid 2
- 每来一条数据，表末尾追加一行
- 写法和 DataFrame 几乎一样
- `read` → `readStream`，`write` → `writeStream`
::: notes
用户只要像写批处理一样写查询，Spark 自动把它变成增量执行。这是 Structured Streaming 最大的好处：第 7、8 章学的写法可以搬过来。
:::

## 读 Kafka 并解析 JSON
```python
raw = (spark.readStream.format("kafka")
       .option("kafka.bootstrap.servers", "kafka:9092")
       .option("subscribe", "orders").load())
orders = (raw.select(F.from_json(F.col("value").cast("string"), schema).alias("o"))
             .select("o.*")
             .withColumn("event_time", F.to_timestamp("event_time")))
```
- 提交时加 `--jars $KAFKA_JARS`（4 个连接器 jar）
::: notes
raw 的列是固定的：key、value（字节）、topic、partition、offset、timestamp。订单内容在 value 里。
:::

## 按时间窗口统计
| 窗口 | 写法 | 适合 |
|---|---|---|
| **滚动窗口** | `F.window("event_time", "1 minute")` | 每分钟成交额 |
| **滑动窗口** | `F.window("event_time", "5 minutes", "1 minute")` | 最近 5 分钟，每分钟刷新 |
- `groupBy(F.window(...), "category")`：每分钟每个品类
::: notes
滚动窗口首尾相接不重叠，每笔订单只属于一个窗口；滑动窗口相互重叠，一笔订单会算进 5 个窗口。
:::

## 输出模式
| 输出模式 | 每批写出什么 | 适合 |
|---|---|---|
| `update` | 这一批中有变化的行 | 大屏、按主键更新数据库 |
| `complete` | 整张结果表 | 结果表很小 |
| `append` | 已经确定、不会再变的行 | 写文件、写 HDFS |
- `trigger(processingTime="10 seconds")`：每 10 秒一批
::: notes
format 常用 console、parquet、kafka，以及 foreachBatch（每批当成普通 DataFrame 处理，可以写 MySQL）。
:::

# 9.5 看懂背后发生了什么

## 事件时间和处理时间
- **事件时间**：事情真正发生的时间（下单时间）
- 处理时间：数据到达 Spark 的时间
- 地铁里断网，20:00 下的单 20:03 才到
- 统计业务指标用事件时间
- 问题：20:00 这一分钟，等到什么时候才算完？

## 水位线：最多等多久
- `withWatermark("event_time", "2 minutes")`
- **水位线** = 见过的最大事件时间 − 2 分钟
- 窗口结束早于水位线：结果定下来，状态清掉
- 再迟到的数据被丢弃
::: notes
水位线是在正确性、延迟和成本之间取舍（Google Dataflow 论文的概括）。交易大屏更看重快，可以设小一些；财务对账更看重准，用批处理兜底。
:::

## 实验 9-3：三种水位线
| 水位线 | 少算的订单 | 最多同时保存的窗口 |
|---|---|---|
| 10 秒 | 83 笔 | 2 个 |
| 2 分钟 | 54 笔 | 4 个 |
| 5 分钟 | 0 笔 | 7 个 |
- 92 笔订单迟到 1～5 分钟
- 等得越久越准，但越慢、越占内存

# 9.6 Flink 与前沿

## Flink 与 Structured Streaming
| 比较项 | Structured Streaming | Flink |
|---|---|---|
| 处理方式 | 默认微批 | 逐条处理 |
| 延迟 | 秒级 | 可到毫秒级 |
| 优势 | 和 Spark 批处理、SQL、机器学习同一套 | 延迟低，状态管理丰富 |
| 国内使用 | 已有 Spark 平台的企业 | 阿里、字节等大规模使用 |
::: notes
事件时间、窗口、水位线、检查点在 Flink 中都有，学会本章再学 Flink 会很快。国内云厂商都有托管 Flink 服务。
:::

## 前沿视窗：实时数仓
- 数仓各层改成一直运行的流处理任务
- 订单一产生，几秒后就能在 ADS 层查到
- 早期：批、流两套代码，口径对不上
- 现在：流式湖仓，一份数据、一套口径

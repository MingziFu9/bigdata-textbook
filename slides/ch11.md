# 11.2～11.3 小文件与 CSV

## 小文件太多
- 现象：任务特别多，每个只跑几毫秒
- 原因：每个文件都有打开开销、占 NameNode 元数据
- 改法：写之前 `coalesce(n)`；定期合并；分区别太细
- 实验 11-1：2000 个小文件 2.57 秒，合并后 0.24 秒
::: notes
小文件通常是自己写出来的：流处理每几秒写一批；Shuffle 后 200 个分区各写一个文件；分区表分得太细。每个文件最好在 128 MB 到 1 GB 之间。
:::

## 课堂练习

## 读 CSV 太慢：换成 Parquet
!sim row-column
- **行式存储**：一行挨一行，要读整行
- Parquet 按**行组**列式存放
- **列裁剪**：只读用到的列
- **谓词下推**：用最小/最大值跳过行组
::: notes
先选第 1 个查询在行式和列式之间切换；再选第 3 个查询，勾选“用最小值/最大值跳过行组”。业务系统用行式，分析系统用列式。
:::

## 实验 11-1：CSV 与 Parquet
| 项目 | CSV | Parquet |
|---|---|---|
| 文件大小 | 239.8 MB | 51.8 MB（22%） |
| 按省统计耗时 | 1.91 秒 | 0.39 秒 |
| 实际要读的数据 | 整个文件 | 3 列约 6.7 MB |
- 执行计划：`ReadSchema` 只有 3 列，`PushedFilters` 有过滤条件
::: notes
Spark UI 在本地文件上显示的 Parquet 读入字节偏小，不能直接比较；程序用“把 3 列单独存一份”估算。
:::

# 11.4 大表关联小表：广播连接

## 两种关联方式
!mermaid 1
- **排序合并连接**：两张表都 Shuffle
- **广播连接**：小表复制到每个执行器，大表不动
::: notes
排序合并连接适合两张大表；大表关联小表时广播连接省掉了大表的 Shuffle。
:::

## 怎么用广播
```python
result = orders.join(F.broadcast(products), "product_id")
```
- 小于 10 MB 自动广播
- 估不准时用 `F.broadcast()`；SQL 写 `/*+ BROADCAST(p) */`
- 别广播大表：几十 MB 以内才合适
- 实验 11-3：关闭广播 1.31 秒，广播 0.58 秒
::: notes
关闭广播后 Shuffle 写出 14.0 MB。几亿行的生产数据上，差距会大得多。
:::

# 11.5 数据倾斜

## 个别任务特别慢
- 现象：进度条到 199/200 不动
- 原因：热点键的数据都进一个任务
- 实验 11-2：s001 占 57% 订单，一个任务处理 170 万行
- 先查热点是不是空值、“未知”、测试账号
- 能广播就广播
::: notes
s001 的订单数是店铺中位数的 514 倍。热点是脏数据的话，过滤掉或单独处理最简单。
:::

## 加盐打散
```python
N = 20
salted_orders = orders.withColumn("salt", (F.rand(seed=7) * N).cast("int"))
salted_shops = shops.withColumn("salt", F.explode(F.sequence(F.lit(0), F.lit(N - 1))))
result = salted_orders.join(salted_shops, ["shop_id", "salt"])
```
- 大表随机加盐，小表复制 N 份
- 最大任务：170 万行 → 17.7 万行；约 1 秒 → 0.2 秒
- 结果不变
::: notes
4 核笔记本上加盐前后总用时差不多（都是 3 秒多）：倾斜时其他 3 个核也没闲着，加盐还多了复制店铺表的开销。几百个核的集群上加盐的效果才明显。
:::

## 动画：数据倾斜与加盐
!sim skew-salt
- 热点 50%、不加盐，比较 4 核与 64 核
- 64 核下把盐调到 4、8、16 份
- 核越多，倾斜的代价越大

## AQE：自适应查询执行
- 运行中按实际数据量调整计划
- 合并小分区：200 个任务合并成 3 个
- 自动改用广播连接
- 拆分倾斜分区：比中位数大 5 倍且超过 256 MB
- 实验 11-2 热点只有 15 MB，AQE 没拆
::: notes
Spark 3.2 起默认打开。小数据演示不会触发倾斜拆分，所以加盐还是要会。
:::

# 11.6 内存不够

## 内存溢出出在哪里
| 出在哪里 | 常见原因 |
|---|---|
| Driver | `collect()`、`toPandas()` 拉回太多；广播太大 |
| 执行器 | 每个任务数据太多：分区太少或倾斜 |
- 编者：300 万行 `collect()` 到 512 MB 的 Driver，报 `OutOfMemoryError`
::: notes
YARN 上常见的还有 Container killed by YARN for exceeding memory limits，常常是堆外内存 memoryOverhead 不够。
:::

## 按顺序试
- ① 不把大数据拉回 Driver
- ② 增加**并行度**：调大 `spark.sql.shuffle.partitions`
- ③ 解决数据倾斜
- ④ 最后才加内存和 `memoryOverhead`
- 参数不是越大越好
::: notes
内存太大，垃圾回收停很久；核太多，任务抢内存。随书环境用本地模式默认值就够了。
:::

# 11.7 性能问题排查表

## 排查表（一）
| 现象 | 原因 | 首先尝试 |
|---|---|---|
| 任务特别多、每个只几毫秒 | 小文件 | `coalesce`、合并 |
| 读入量接近整个文件 | CSV 行式文本 | 换 Parquet、只选需要的列 |
| 大表关联小表、两个大 Shuffle | 排序合并连接 | `F.broadcast()` |
| 最大值是中位数几十倍 | 数据倾斜 | 查脏数据、广播、加盐 |

## 排查表（二）
| 现象 | 原因 | 首先尝试 |
|---|---|---|
| Driver 报 OOM | 拉回太多、广播太大 | 只拉回聚合结果 |
| 执行器 OOM、Spill 很大 | 每个任务数据太多 | 加分区、处理倾斜 |
| 同一结果反复从头算 | 没有缓存 | `cache()`，用完 `unpersist()` |
| 所有任务都均匀地慢 | 计算量大或 Python UDF | 用内置函数；加机器 |
::: notes
排查顺序：先看格式和数据量，再看 Shuffle，再看任务分布，最后才调内存参数。越靠前的改法越简单、收益越大。
:::

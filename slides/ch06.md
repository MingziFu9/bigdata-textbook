# 6.1 Spark 解决什么问题

## 比 MapReduce 快在哪
| 比较项 | MapReduce | Spark |
|---|---|---|
| 一个程序几步 | 固定 Map + Reduce | 任意多步 |
| 中间结果 | 写进 HDFS | 尽量放内存 |
| 反复用同一份数据 | 每次重读 | 可以缓存 |
| 写程序 | mapper、reducer 分开写 | 像普通 Python 串操作 |
::: notes
伯克利 2009 年开始研发，后捐给 Apache。机器学习要迭代几十遍，Spark 的优势最明显。
:::

# 6.2 看懂背后发生了什么

## Driver 和 Executor
!mermaid 1
- **Driver**：运行主程序，拆任务、收结果
- **Executor**：在工作节点上运行任务、缓存数据
- 集群管理器：本地模式或 YARN
::: notes
print 和 collect 的结果都在 Driver。和 MapReduce 不同，Executor 启动一次能接连跑很多任务。
:::

## RDD：分成很多块的数据集
- 想成“分散在各 Executor 上的大列表”
- **分布式**：切成多个分区，一个分区一个任务
- **弹性**：记得自己的由来，丢了分区就重算
- 只读：每次操作都产生新的 RDD

## 转换和行动
| 类别 | 例子 | 什么时候执行 |
|---|---|---|
| **转换** | `map`、`filter`、`reduceByKey`、`join` | 不马上执行，只记下怎么算 |
| **行动** | `count`、`collect`、`take`、`saveAsTextFile` | 立刻触发计算 |
::: notes
实验 6-1：定义三个转换 0.6 秒（根本没读文件），count 时才读 70 MB 日志，2.1 秒。这就是惰性执行。
:::

## 惰性执行的好处
- Spark 先看全局，再决定怎么算
- `map` 后紧跟 `filter`：每行读进来一次做完
- 只要 `take(10)`：可能只读一小部分
- 记住：**没有行动，什么都不会发生**

# 6.3 运行 Spark 程序的几种方式

## 随书环境：加一个 Spark 容器
- 新配置 `docker-compose.spark.yml`
- 官方镜像 Spark 4.1.4，自带 Java 21
- `labs` 同样挂载在 `/labs`
- 第 6～8 章实验都在 spark 容器里做
::: notes
命令要带 -f docker-compose.yml -f docker-compose.spark.yml。不在 Windows 本机装 PySpark，是因为写文件还要额外工具、访问不到 HDFS 数据节点。
:::

## pyspark 与 spark-submit
| 方式 | 适合 | 要点 |
|---|---|---|
| `pyspark` | 学习、试验 | 已建好 `spark`、`sc` |
| `spark-submit x.py` | 运行写好的程序 | 自己建 SparkSession |
::: notes
Spark UI 地址显示的是容器名 spark，浏览器里换成 localhost:4040。
:::

## 本地模式还是提交到集群
| 方式 | 写法 | 适合 |
|---|---|---|
| 本地 | `--master local[*]` | 学习、调试、单机放得下 |
| YARN | `--master yarn` | 数据在 HDFS、量大 |
- `file:///labs/...` 是本地文件；不写 `file://` 是 HDFS
- 实测 1000 万行：本地 10.6 秒，YARN 32.1 秒（总计 53 秒）
::: notes
随书集群几个节点挤在一台电脑上，集群反而慢。集群的优势要在真正多台机器、单机放不下的数据上体现。
:::

# 6.4 RDD 常用操作

## 创建 RDD
| 写法 | 得到什么 |
|---|---|
| `sc.textFile("file:///labs/...")` | 本地文件的每一行 |
| `sc.textFile("/xiaoxiang/logs/*.log")` | HDFS 文件的每一行 |
| `sc.parallelize([1, 2, 3])` | Python 列表变 RDD |

## 常用转换
| 操作 | 作用 |
|---|---|
| `map` | 一进一出 |
| `flatMap` | 一进多出，结果压平 |
| `filter` | 只留条件为真的 |
| `distinct` | 去重（Shuffle） |
| `reduceByKey` | 同键的值两两合并（Shuffle） |
| `sortBy`、`join` | 排序、按键拼接（Shuffle） |

## 常用行动
| 操作 | 作用 |
|---|---|
| `count` | 元素个数 |
| `take(n)` | 取前 n 个 |
| `takeOrdered(n, key=...)` | 排序后取前 n 个 |
| `collect` | 全部取回 Driver |
| `saveAsTextFile` | 写成目录，每个分区一个文件 |
::: notes
键值对 RDD：元素是 (键, 值)。map(lambda x: (x, 1)) 就是 Map 阶段，reduceByKey 就是 Shuffle + Reduce。
:::

## 两个常见的坑
- `collect()` 把全部数据拉回 Driver，大数据会撑爆内存
- 看数据用 `take(10)`，存结果用 `saveAsTextFile`
- 能用 `reduceByKey` 就别用 `groupByKey`
- `reduceByKey` 先在分区内合并，Shuffle 数据少得多

# 6.5 用 RDD 改写日志统计

## 三个统计放进一个程序
```python
fields = lines.map(lambda l: l.split()).filter(lambda f: len(f) == 8)
fields.cache()
pv = fields.map(lambda f: (f[0][11:13], 1)).reduceByKey(lambda a, b: a + b)
top10 = (fields.filter(lambda f: f[5] == "200")
               .map(lambda f: (f[4], 1)).reduceByKey(lambda a, b: a + b)
               .sortBy(lambda kv: kv[1], ascending=False).take(10))
```
::: notes
结果与第 4 章完全相同：21 点 PV 88286、UV 43162，/search 108159 次。UV 用 distinct 去重后再计数。
:::

## MapReduce 与 RDD 对比
| 比较项 | 第 4 章 MapReduce | 本章 RDD |
|---|---|---|
| 文件 | 5 个 Python + 1 个 Shell | 1 个 Python |
| 有效代码 | 约 104 行 | 约 27 行 |
| 运行 | 2 个作业，各 20～25 秒 | 1 个程序，约 11 秒 |
::: notes
代码短：排序、分组、判断键变化这些琐事 Spark 做了。速度快：三个统计共用一次读入，中间结果不写 HDFS。
:::

# 6.6 缓存什么时候用

## cache：算一次，用多次
- 每个行动都从头执行一遍转换
- `fields` 被用三次 → 先 `cache()`
- 实测：第一次 count 1.1 秒，第二次 0.17 秒
- 只用一次不缓存；`cache()` 本身也是惰性的
::: notes
用完 unpersist() 释放。Storage 页面能看到缓存；内存放不下的分区会丢掉，下次重算，结果不会错。
:::

## 实验常见问题
- 打不开 4040：程序已经结束；同时跑两个程序会改用 4041
- `Path does not exist: hdfs://...`：本地文件忘了写 `file:///`
- YARN 上读不到本地文件：Executor 只能读 HDFS
- 小时顺序乱：`collect()` 回来不保证顺序，用 `sorted()`
- 一直 ACCEPTED：资源被别的作业占着

## 本章小结
- Spark 中间结果放内存，多步计算连成一条流水线
- Driver 拆任务、收结果；Executor 跑任务、存缓存
- 转换惰性执行，行动触发 Job；Shuffle 切开 Stage
- 本地模式调试，大数据提交到 YARN
- 同一 RDD 用两次以上才缓存

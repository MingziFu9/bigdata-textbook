## 学习目标
- **说出** Map、Shuffle、Reduce 三个阶段和 YARN 的四个角色
- **解释**分区和 Combiner 的作用，Shuffle 为什么最费时
- **编写** Python 版 mapper / reducer，用 Hadoop Streaming 提交
- **判断**一个需求用哪种写法、能不能加 Combiner
- **排查**作业失败或卡在 ACCEPTED 的原因
::: notes
本章 5 学时理论 + 1 学时实验。Hadoop 三大组件：HDFS 负责存，YARN 负责分资源，MapReduce 负责算。重点是“看懂数据怎样流动”和“会用 Python 写、会看网页排错”，不要求背 Java API。
:::

- 9 月 30 日每小时有多少次浏览（PV）？
- 每小时有多少个不同的用户（UV）？

# 4.1 MapReduce 解决什么问题

## 分而治之：阅卷的例子
- 2 万份卷子，一位老师要批几个星期
- 分给 100 位老师，每人 200 份，**同时批**
- 最后只需把“同一道题”的分数汇总
- 2004 年谷歌把这套做法总结为 **MapReduce**
::: notes
强调两个前提：各自批改互不干扰（Map 可并行）；汇总只需把相同的题放在一起（按键汇总）。
:::

## 你写两个函数，剩下的交给框架
| 函数 | 输入 | 输出 |
|---|---|---|
| Map | 一行原始数据 | 若干个键值对 |
| Reduce | 一个键和它的所有值 | 汇总结果 |
::: notes
框架负责：切分数据、分配机器、失败重试、把相同的键送到一起、数据本地化。作业（Job）由许多任务（Task）组成，任务失败只重跑任务。
:::

# 4.2 看懂背后发生了什么

## 一个作业的三个阶段
!mermaid 2
- 一个分片 → 一个 Map 任务
- Shuffle：分区、排序、拉取、合并
- 每个 Reduce 写一个 part 文件
::: notes
Map 和 Reduce 都是各干各的，只有 Shuffle 要在机器之间交换数据：写磁盘、走网络、排序，所以最费时。实验 4-3 中 Shuffle 搬运了 122 MB。
:::

## 算一算：三行搜索关键词
| Map 任务 | 输入 | 输出 |
|---|---|---|
| Map 0 | 手机 耳机 充电宝 | (手机,1) (耳机,1) (充电宝,1) |
| Map 1 | 耳机 耳机 手机 | (耳机,1) (耳机,1) (手机,1) |
| Map 2 | 充电宝 手机 鞋 | (充电宝,1) (手机,1) (鞋,1) |
::: notes
请学生先在纸上推，再翻下一页对答案。2 个 Reduce：充电宝、耳机进分区 0；手机、鞋进分区 1。
:::

## Shuffle 和 Reduce 的结果
| Reduce | 拉取并分组 | 输出 |
|---|---|---|
| Reduce 0 | 充电宝 → [1,1]；耳机 → [1,1,1] | 充电宝 2，耳机 3 |
| Reduce 1 | 手机 → [1,1,1]；鞋 → [1] | 手机 3，鞋 1 |
::: notes
两个要点：同一个词只出现在一个输出文件里；结果分在两个 part 文件，合起来才是完整结果。和实验 4-1 模拟程序、真实集群的输出完全一致。
:::

## 分区：同一个键只去一个 Reduce
- 规则：键的哈希值 ÷ Reduce 个数，取**余数**
- 同一个键在哪个 Map 里，余数都一样
- Reduce 有几个，就有几个 part 文件
- 键少时可能分不均，出现空文件
::: notes
实验 4-1 中改成 3 个 Reduce，1 号 Reduce 一个键也没有分到，输出空文件。
:::

## Combiner：先在本地汇总一次
- Map 1 的两个 (耳机,1) 先合成 (耳机,2)
- 三行例子：Shuffle 从 9 条变 8 条
- 1000 万行日志：122.4 MB → **0.2 MB**
- 相当于每位老师先交一张小统计表
::: notes
Combiner 的结果还要被 Reduce 再汇总一次，所以只适合“分步算和一次算结果相同”的统计。
:::

## 哪些统计能用 Combiner
| 计算 | 能否直接用 | 原因 |
|---|---|---|
| 求和、计数 | 能 | 分组加再总加，结果不变 |
| 最大值、最小值 | 能 | 各组最大的最大就是总最大 |
| 平均值 | 不能 | 平均的平均 ≠ 总平均 |
| 去重计数（UV） | 不能 | 两组各 10 人，合起来可能只有 15 人 |

## 动画：一步一步看数据流动
!sim mapreduce-wordcount
- 颜色 = 分区
- 改 Reduce 个数、勾 Combiner
- 计数器和 Hadoop 同名

# 4.3 用 Python 写 MapReduce 程序

## Hadoop Streaming 怎样工作
- mapper、reducer 是普通 Python 程序
- 从**标准输入**读，向**标准输出**写
- 每行“键 Tab 值”
- reducer 收到的数据**已按键排好序**
::: notes
和 Java 版的区别：reducer 拿到的不是“键 + 值列表”，而是一行一行排好序的数据，要自己判断键什么时候变了。
:::

## reducer 的固定套路：换键时输出
```python
current_word, current_count = None, 0
for line in sys.stdin:
    word, count = line.rstrip("\n").split("\t")
    if word == current_word:
        current_count += int(count)
    else:
        if current_word is not None:
            print(f"{current_word}\t{current_count}")
        current_word, current_count = word, int(count)
if current_word is not None:
    print(f"{current_word}\t{current_count}")
```
::: notes
最容易漏掉最后两行：循环结束时最后一个键还没输出。
:::

## 先在本机用管道调试
```bash
cat data/search_words.txt | python3 ch04/wc_mapper.py | sort | python3 ch04/wc_reducer.py
head -20000 data/xiaoxiang/access.log | python3 ch04/pv_mapper.py | sort | python3 ch04/pv_reducer.py
```
- `sort` 相当于 Shuffle 的排序，**不能省**
- 管道能跑通，集群上一般就能跑通
::: notes
本机调试三个好处：报错直接可见、几秒出结果、能和集群结果对照。
:::

## 提交到集群：mapred streaming
| 参数 | 含义 |
|---|---|
| `-D mapreduce.job.name=…` | 作业名，显示在 8088 网页 |
| `-D mapreduce.job.reduces=N` | Reduce 个数 |
| `-files a.py,b.py` | 分发脚本，**最常漏** |
| `-mapper` / `-reducer` / `-combiner` | 运行命令 |
| `-input` / `-output` | 输出目录**必须不存在** |
::: notes
结束时看计数器：Map input records 应等于日志行数；Reduce output records 为 0 多半是输出格式错了。输出目录里的 _SUCCESS 表示成功。
:::

# 4.4 三种常用写法

## 先想清楚：键是什么，值是什么
| 写法 | 例子 | 键 | 值 | Combiner |
|---|---|---|---|---|
| 计数求和 | 页面访问次数 | 页面 | 1 | 能 |
| 去重计数 | 每小时 UV | 小时 | 用户 | 不能 |
| 排行榜 | 前 10 页面 | 页面 | 1 | 求和部分能 |
::: notes
翻译成 SQL：键就是 GROUP BY 的列，Reduce 做的就是 SUM、COUNT、MAX。到了 Hive 和 Spark SQL 这个本领照样用得上。
:::

## 写法要点
- mapper 要**跳过坏数据**：`if len(fields) != 8: continue`
- UV：同一小时的用户放进 `set()` 去重
- 未登录访客 `-` 不计入 UV
- TopN：用 `heapq` 只保留 10 个，**只能 1 个 Reduce**
::: notes
问学生：TopN 用 2 个 Reduce 会怎样？每个 Reduce 只看到一半的页面，合起来是 20 个“前 10 名”，不是全局前 10。
实验 4-2 结果：高峰在 20～22 点，21 点 PV 88286、UV 43162，是凌晨 2 点的 13 倍多；最热的是搜索页和首页，商品 p01372 访问 66234 次。可以和学生讨论怎样据此安排大促推送和客服排班。
:::

# 4.5 YARN：集群的调度中心

## 四个角色
| 角色 | 几个 | 做什么 |
|---|---|---|
| ResourceManager | 集群 1 个 | 掌握全局资源，决定分给谁 |
| NodeManager | 每台机器 1 个 | 汇报本机资源，启动容器 |
| ApplicationMaster | 每个作业 1 个 | 申请资源、安排任务、重试 |
| 容器 Container | 很多 | 一份内存和 CPU，任务在里面跑 |
::: notes
类比物流公司：调度中心、仓库管理员、项目经理、工位。提醒：YARN 容器不是 Docker 容器。YARN 让 Spark、Flink 也能共用一个集群。
:::

## 一个作业的一生
- 提交 → **ACCEPTED**（等 AM 的容器）
- 启动 AM → **RUNNING**
- AM 申请容器，先跑 Map，再跑 Reduce
- 任务失败自动重试，最多 4 次
- 全部完成 → **FINISHED**，资源收回
::: notes
算一算：随书集群 2 × 2048 ÷ 512 = 8 个容器。1 个 AM + 6 个 Map 一批跑完；2 GB 日志 16 个 Map 要分三批。
:::

## 动画：资源怎样分配
!sim yarn-scheduling
- 改节点数、内存、作业大小
- 勾选作业 B：为什么停在 ACCEPTED？
- 1 个节点 + 2 GB 容器：卡住了
::: notes
现场演示三个场景：默认；2 GB 输入分批运行，再加到 4 个节点；勾选作业 B，解释 AM 资源上限 10%。
:::

## 作业失败：三步找原因
- 找任务：`attempt_…_m_000000_0`，看尝试了几次
- 看 stderr：`yarn logs -applicationId … -log_files stderr`
- 对症改：code 2 漏 `-files`；code 1 程序异常；127 找不到命令
::: notes
真实案例：漏写 -files，stderr 里是 can't open file …/pv_mapper.py。
:::

## 作业卡在 ACCEPTED
- AM 总共只能占集群资源的 **10%**
- 随书集群 4096 MB 的 10% 放不下第二个 AM
- 节点 UNHEALTHY（磁盘快满）也会卡住
- 申请的容器大于任何一台机器的内存
::: notes
随书集群实测：同时提交两个作业，第二个一直 ACCEPTED，第一个结束后才开始跑。
:::

# 4.6 局限与今天的选择

## MapReduce 的局限
- **慢**：启动十几秒，中间结果反复读写磁盘
- 70 MB 日志：集群约 25 秒，本机管道不到 10 秒
- **繁**：一个统计两个程序，多步要串作业
- 不适合迭代计算和实时计算
::: notes
数据小的时候单机更快，集群的优势要到单机处理不了时才显现。今天的选择：几 GB 以内用 pandas；SQL 查大表用 Hive（第 5 章）；批量清洗统计用 Spark（第 6～8 章）；实时处理用 Kafka + 流计算（第 9 章）；大数据机器学习用 Spark MLlib（第 10 章）。
:::

## 前沿视窗：大模型数据处理
- FineWeb：96 期网页快照 → 约 15 万亿词元
- 逐份过滤清洗是 Map，找重复要按键分组
- 国产 Data-Juicer：50 多个算子，可用 Ray 分布式运行
- 长文档摘要：先分段总结，再合并总结
::: notes
“分给很多人各做一份、最后汇总”的思想在大模型时代依然好用。
:::
